## ⚠️ Critical Blocker — OpenProject API Limitation

> [!CAUTION]
> **The sprint spec assumes `GET /api/v3/roles/:id` returns a `permissions` array. It does not.**
>
> Confirmed from two sources:
> 1. The [role_representer.rb](file:///home/iosamaayaz/Coding/FYP Stuff/openproject-private-clean/lib/api/v3/roles/role_representer.rb) in this very codebase is explicitly marked `# TODO: This is only a stub` and exposes only `id` and `name`.
> 2. The OpenProject public API v3 documentation confirms that permissions are not exposed on role entities. OpenProject uses HAL action links per resource and an internal ACL, not a permissions array on the role.
>
> A real `GET /api/v3/roles/3` returns:
> ```json
> { "_type": "Role", "id": 3, "name": "Manager", "_links": { "self": { "href": "/api/v3/roles/3" } } }
> ```
>
> **There is no `permissions` field.**

## Open Questions

> [!IMPORTANT]
> **1. How should `get_role_permissions` be implemented given the API limitation?**
>
> There are two viable strategies. Please choose one:
>
> **Option A — Extend the role representer (backend change)**
> Add `property :permissions` to [role_representer.rb](file:///home/iosamaayaz/Coding/FYP Stuff/openproject-private-clean/lib/api/v3/roles/role_representer.rb). The `Role` model already has a `permissions` method (line 113 of [role.rb](file:///home/iosamaayaz/Coding/FYP Stuff/openproject-private-clean/app/models/role.rb)) that returns an array of permission symbols. This is the cleanest approach and makes the BFF genuinely use the real API, but it requires a small Rails change.
>
> **Option B — Hard-code or config-drive a local permission map**
> Define a `ROLE_PERMISSIONS` dict in the Python service that maps known role IDs (or names) to their permission lists. `get_role_permissions` looks up the dict instead of hitting the API. The sprint's test mocks will still work, but real integration will need the map to be kept in sync manually.
>
> My recommendation: **Option A**. The representer change is 1 line of Ruby, properly integrates with the real OpenProject instance, and is the architecturally correct path.

> [!IMPORTANT]
> **2. What shape should the `permissions` field take in the API response?**
>
> *(Only relevant if you choose Option A.)*
>
> The Rails `Role#permissions` method returns an array of Ruby symbols (e.g. `[:edit_work_packages, :view_work_packages]`). These serialize to JSON as strings. The Python `PermissionSet.permissions` field would then be `list[str]` (e.g. `["edit_work_packages", "view_work_packages"]`). Is that the expected format for downstream consumers (e.g. the LLM/intent handler in later tasks)?

> [!IMPORTANT]
> **3. Concurrency for role permission fetches?**
>
> `get_user_permissions` calls `get_role_permissions` once per role the user holds in the project. If a user has 3 roles, that's 3 sequential API calls. I plan to run them **concurrently** using `asyncio.gather()`. This is correct for an async service and matches the client's design. Acceptable?

### Python service additions

#### [MODIFY] [permissions_service.py](file:///home/iosamaayaz/Coding/FYP Stuff/openproject-private-clean/adaptive_ui_service/app/services/permissions_service.py)

Add below the existing code:

```python
import asyncio

@dataclass
class PermissionSet:
    user_id: int
    project_id: int
    permissions: list[str]


async def get_role_permissions(role_id: int, client: OpenProjectClient) -> list[str]:
    data = await client.get(f"/api/v3/roles/{role_id}")
    return data.get("permissions", [])


async def get_user_permissions(
    user_id: int, project_id: int, client: OpenProjectClient
) -> PermissionSet:
    memberships = await get_user_memberships(user_id, client)

    project_membership = next(
        (m for m in memberships if m.project_id == project_id), None
    )
    if project_membership is None:
        return PermissionSet(user_id=user_id, project_id=project_id, permissions=[])

    role_permissions_lists = await asyncio.gather(
        *[get_role_permissions(role_id, client) for role_id in project_membership.role_ids]
    )

    seen: set[str] = set()
    deduped: list[str] = []
    for perms in role_permissions_lists:
        for perm in perms:
            if perm not in seen:
                seen.add(perm)
                deduped.append(perm)

    return PermissionSet(user_id=user_id, project_id=project_id, permissions=deduped)
```

**Design decisions:**

| Decision | Rationale |
|---|---|
| `next(..., None)` for membership lookup | Avoids a list comprehension + index error; returns `None` cleanly when user has no membership |
| Empty `PermissionSet` (not error) for non-members | Spec says "assert empty PermissionSet, no error" |
| `asyncio.gather` for concurrent role fetches | Parallelises N API calls; especially valuable if a user has multiple roles |
| Ordered deduplication (not `set`) | Preserves insertion order, making output deterministic for the same input — important for downstream LLM use |
| `data.get("permissions", [])` | Defensive: if `permissions` key is missing (e.g. calling against an unpatched OpenProject), returns empty list rather than crashing |
